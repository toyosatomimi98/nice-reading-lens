# 方案落地说明

对着《AI 纸质书智能翻译阅读器 V0.1》逐条说这一版做到哪儿了。方案里没写的实现细节，挑有取舍的地方写清楚原因。

## 一句话结构

手机是传感器，电脑是大脑。手机只负责持续回传低分辨率预览帧，要不要动 OCR 由电脑判断；判断成立之后，电脑再让手机抓一张高清图。

这么分有两个好处：手机端一行识别代码都没有，换设备不用改逻辑；判断标准全在电脑上，调参不用重新加载手机页面。

## 逐节对照

### 01 项目目标

做到了。翻页 → 稳定 → 高清采集 → OCR → 版面 → 翻译 → 呈现，这条链路完整跑通，全程在局域网内，翻译不出本机。

### 02 产品原则

| 原则 | 落地方式 |
| --- | --- |
| 不加硬件 | 只用 iPhone + 支架 + Windows。少一样也能跑，手动上传照片即可 |
| 持续监测不等于持续推理 | 预览帧只有 480px 宽、0.8 秒一张，单帧判断不到 5ms，不加载任何模型；OCR 和翻译只在确认翻页后跑一次 |
| 一次识别，多种呈现 | 一页只存一份 `blocks`（原文 + 译文 + 坐标 + 类型），三种模式都是它的不同渲染 |
| 阅读位置连续 | 切换模式时记录「当前视口顶部是哪个块、偏了多少像素」，渲染完再滚回去 |
| 低视觉扰动 | 新页准备好之前继续显示旧页，只换状态提示文字 |
| 高频在工具栏，低频在设置 | 模式切换和原图核对在顶栏，其余二十来个参数在抽屉里 |

### 03 系统架构

五层都在，但比方案画得薄：

- **iPhone Safari**：`getUserMedia` 取景，canvas 缩放后回传。拍照前临时把约束抬到 3840×2160，等 0.4 秒再截帧，然后降回预览分辨率。iOS 上 `ImageCapture` 不可用，这是目前唯一现实的做法。
- **局域网通信**：HTTPS（自签证书，SAN 里带局域网 IP）+ WebSocket + 普通 POST。证书是 `run.py` 用 openssl 现签的，有效期 820 天，在 iOS 的 825 天上限内。
- **电脑后端**：FastAPI + uvicorn。CPU 上跑 OCR 和图像处理，走线程池，不阻塞事件循环。
- **统一文档数据**：见下面「数据结构」。
- **电脑前端**：原生 HTML/CSS/JS，没有构建步骤，改完刷新就见效。

### 04 事件驱动的图像处理

状态机在 `app/gate.py`，四个状态：`idle`（还是原来那页）→ `candidate`（画面变了）→ `confirm`（新画面稳住 N 帧）→ `cooldown`（确认后静默几秒，等手机把高清图传完）。

**判据是墨迹掩码的杰卡德距离**，不是灰度平均差。这是这一版里改动最大的一个决定，理由见「关键取舍」。

方案里说「翻页事件与新页面确认是两件事」，代码里就是 `candidate` 和 `confirm` 两个状态：画面在动的时候一直是 `candidate`，只有连续三帧（约 2.4 秒）画面基本不动了才 `confirm`。

### 05 文档理解与翻译

**版面**（`app/layout.py`）是启发式，不是版面分析模型：

- 先估行距（同一栏里相邻两行顶边的中位距离），行距和横向重叠决定哪些行属于同一段。
- 标题：字号明显大于正文且短，或者以 Chapter/Part/Section 开头，或者整行大写。
- 图表说明：以 Figure/Table/Exhibit 加编号开头。
- 公式：数学符号占比超过 10%。
- 页眉页脚：孤立且极短的首尾行，以及纯页码。
- 阅读顺序：先按左右页，页内按从上到下、从左到右。

**OCR** 用 RapidOCR——PaddleOCR 模型的 ONNX 发行版。选它的原因是不用装 paddlepaddle，模型跟着包走，CPU 上单页 1~3 秒。方案里写的 PaddleOCR 是同一条技术路线。

**翻译** 走本机 Ollama。带上三样东西：用户词表、上一页结尾的原文和译文（各 320 字符）、严格编号的段落列表。输出用 `@@1@@` 这样的哨兵分隔，解析失败先重试一次，还是不行就退化成逐段翻译——慢一点，但不会整段错位。

跨页段落只做了「带前文上下文」这一层，没有做「把跨页段落拼成一个完整段落」。方案里写的是前者，够用。

### 06 三种阅读模式

都实现了，共用一份数据。

- **轻量**：左图右译文。鼠标划过右侧段落，左边图上对应的框亮起来并滚到可见位置。
- **标准**：英文在上、译文在下，按阅读顺序排。标题和图表说明单独排版。
- **沉浸**：图上按坐标盖白底中文框，字号自动缩放到框内；缩到 10px 还塞不下就停止缩小，改让框向下长，最多长到 1.5 倍。点击框弹出英文原文。

方案说沉浸模式「可先使用 HTML/CSS 覆盖层，后续再考虑图像修复」，这一版就是覆盖层，没碰像素。

### 07 低干扰交互与设置

状态提示走的是真实阶段：`收到书页，正在摆正` → `正在识别文字` → `正在翻译 N 段` → `第 N 页就绪（识别 x.xs，翻译 x.xs）`。没有百分比，因为没法算准。

新页到达时，如果你正停在最新一页，自动切过去；如果你在往回翻旧页，不打断你，只在底部弹一条可以点着跳过去的提示。

### 08 技术候选与验证

| 方向 | 方案候选 | 这版实际用的 |
| --- | --- | --- |
| 摄像头与传输 | getUserMedia / Canvas / FastAPI / HTTPS / WebSocket | 全用了 |
| 翻页与预处理 | OpenCV / 图像差分 / 感知哈希 / 透视校正 / 双页分割 | 全用了，图像差分换成了墨迹掩码距离 |
| 识别与翻译 | PaddleOCR / 版面分析 / VLM / LLM API / 本地模型 | RapidOCR + 本地 Ollama |
| 渲染与交互 | HTML/CSS/SVG / 统一块 ID / 阅读锚点 / 异步状态 | 全用了，没上 SVG |
| 设备稳定性 | 长时间前台采集 / 发热 / 断线重连 | 申请了屏幕常亮，WebSocket 断线自动重连，切后台会暂停 |

VLM 没用上。`qwen3-vl:8b` 就在本机，但整页 VLM 识别比 RapidOCR 慢一个数量级，准确率优势在印刷体上不明显。真正值得用 VLM 的场景是图文混排和低置信度页面的补读，那属于下一步。

### 09 主要技术风险

| 风险 | 这一版的状态 |
| --- | --- |
| 小字、书脊弯曲、阴影降低 OCR 准确率 | 有对比度增强和透视校正；书脊弯曲没做专门处理 |
| 翻页检测受手部遮挡、光照、书本移动干扰 | 墨迹掩码对整体明暗不敏感，实测整页变亮只引起 0.035 的距离；手遮挡仍是弱项 |
| 图表公式导致阅读顺序错误 | 顺序靠几何位置，没有真实版面分析，复杂版式会错 |
| 中文长度变化导致原位覆盖不可读 | 沉浸模式有 10px 下限和向下生长，再长会截断 |
| iOS 高清采集能力待实测 | 采集页显示实际分辨率，留给真机验证 |
| OCR 翻译排版延迟 | 异步 + 缓存。重启后重复页面命中缓存，翻译耗时接近 0 |

### 10 范围边界

方案说不做的，这版也没做：iOS 原生 App、锁屏持续采集、USB 摄像头、云端多人协作、Android 专门适配。Android 上理论上直接能用（Chrome 支持 getCamera + ImageCapture），但没验证过。

## 关键取舍

### 翻页判据为什么不用灰度平均差

桌上拍的一页书，绝大部分像素是白纸。两页之间真正不同的只有文字笔画那点面积，所以灰度平均差很小。实测：

| 情况 | 灰度平均差 | 墨迹掩码距离 |
| --- | --- | --- |
| 同一页 + 相机噪点 | 0.021 | 0.033 |
| 整页变亮 | 0.010 | 0.035 |
| 翻页（满页正文） | 0.101 | 0.772 |
| 翻页（稀疏页面） | **0.015** | 0.770 |
| 翻页中的运动模糊 | 0.129 | 0.863 |
| 手挡住一栏 | 0.045 | 0.383 |

看第三、四行：稀疏页面翻页的平均差 0.015 比噪点的 0.021 还小，任何能挡住噪点的阈值都必然漏掉这次翻页。墨迹掩码距离不受页面多满、整体多亮影响，稀疏页和满页都是 0.77 左右。

掩码是每帧自己跑 Otsu 分出来的，所以整体亮度变化时分出来的形状基本不变——这正是它对光照不敏感的原因。阈值定在 0.30，离噪点的 0.03 和翻页的 0.77 都很远。

### 页摆正为什么要挑「合格里最大」而不是「最大」

第一版取的是最大四边形，结果深色桌面上书页那一版掩码是「背景是前景、书页是洞」，最大四边形是整幅画面，于是判断成「已经贴满画面，不用矫正」，摆正永远不生效。改成先按面积比例、是否贴边、长宽比筛掉不合格的，再从合格的里挑最大的。

### 为什么另建虚拟环境

一开始直接把依赖装进了 Anaconda 的 base 环境，pip 顺手把 numpy 升到了 2.x，把 base 里的 scipy、numba、gensim 全弄成了不兼容。已经装回 numpy 1.26.4 并把多装的包卸掉了，项目改用自带的 `.venv`。

## 数据结构

一页就是一个 JSON，三种模式全部由它渲染：

```json
{
  "id": "p003",
  "index": 3,
  "width": 2600, "height": 1800,
  "rectified": true,
  "split": ["left", "right"],
  "hash": 1234567890123456789,
  "blocks": [
    {
      "id": "p003b02",
      "order": 2,
      "type": "paragraph",
      "side": "left",
      "rect": [218, 362, 1243, 720],
      "text": "The transformer replaced recurrence with...",
      "zh": "Transformer 用一个更简单的想法替代了循环……",
      "confidence": 0.988,
      "font_height": 43.0
    }
  ],
  "elapsed_ms": { "ocr": 3100, "translate": 2700, "total": 6100 },
  "engine": { "ocr": "RapidOCR", "mt": "qwen3:8b", "source": "phone" }
}
```

`rect` 是 `[x0, y0, x1, y1]`，坐标属于摆正之后的整幅画面（双页时左右页的坐标都已经加回全局），所以沉浸模式的覆盖框可以直接按比例定位。

## 实测数据

在 RTX 5060 Ti + Windows，OCR 跑 CPU、翻译跑 GPU 的环境下：

- RapidOCR 单页 1.2~2.0 秒；一个双页展开（两块正文 + 标题 + 图注）约 3.2 秒。
- 翻译 12 段约 8.4 秒；同样的内容第二次走缓存，0.0 秒。
- 一个双页展开从上传到就绪约 6 秒，其中识别 3.1 秒、翻译 2.7 秒。
- 首次启动要加载 OCR 模型和唤起 Ollama 模型，第一页会多花 5 秒左右。

翻页检测单帧（480px JPEG 解码 + 缩放 + 掩码 + 比对）不到 5 毫秒。
