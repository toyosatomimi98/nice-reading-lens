## 看方案

先把 PDF 读了。直接抽文字出来是乱码——PDF 里的中文字体没做 Unicode 映射，读到的是字形编码。改成渲染成图再看，四页都看完。

## 先摸环境

这台机器上：RTX 5060 Ti 16G，Ollama 已经在 `127.0.0.1:11434` 上跑着，模型里 `qwen3:8b`、`qwen3:14b-32k`、`qwen3-vl:8b` 都有。Python 是 Anaconda 的 3.12。

没有 OCR 引擎，没有 ffmpeg，没有 tesseract。openssl 有，Git 自带的那个能用来签证书。

OCR 选型想了下：PaddleOCR 完整版要装 paddlepaddle，几百兆；`rapidocr-onnxruntime` 是同一套模型的 ONNX 版，模型跟着 wheel 走，CPU 就能跑。先用它试了一张合成书页，识别 1.7 秒，置信度 0.98 以上，够用，就定了。

翻译直接试了三个模型，同一段文本：`qwen3:8b` 6.8 秒、`qwen3:14b-32k` 9.2 秒、`qwen2.5:14b` 11.4 秒，质量都能用。默认选了快的那个，设置里可以换。

## 装依赖踩的坑

这个得记一下。我图省事，直接把依赖装进了 Anaconda 的 base 环境，结果 pip 顺手把 numpy 从 1.26.4 升到了 2.5.3，base 里的 scipy、numba、gensim、contourpy 全部报不兼容。这不是我该动的东西。

处理方式：新建项目自己的 `.venv`，依赖装进去；然后把 base 环境里多出来的包全卸掉，numpy 装回 1.26.4，protobuf 也装回原来的 4.25.3。现在 base 环境跟动手前一样。

顺便发现 opencv 5.0 要求 numpy ≥ 2，所以 requirements 里写 `opencv-python` 而不是 headless——rapidocr 本来就会拉 opencv-python，两个都写会白装一份 44MB。

翻页检测单独一个文件，因为这块的逻辑最容易写乱。翻译单独一个文件，因为提示词和解析要反复调。

最后是 `pipeline` 把上面串起来，`server` 挂路由，前端两个页面。

## 翻页检测：返工了一次

第一版判据是「两帧的平均灰度差」，阈值 0.055。写完拿两张不同的书页一测，全是 `idle`，一次都没触发。

想了下原因：桌面上拍的书页大部分像素是白纸，两页真正不同的只是文字笔画那一小块面积。合成了两种页面来量化——满页正文和稀疏页面——量出来是这样：

```
                              平均灰度差   墨迹掩码距离
密集页 同页+噪声                  0.021        0.033
密集页 换页                       0.101        0.772
稀疏页 换页                       0.015        0.770
整页变亮                          0.010        0.035
翻页中的运动模糊                  0.129        0.863
手挡住一栏                        0.045        0.383
```

关键在「稀疏页换页」这一行：0.015，比同页噪点的 0.021 还小。也就是说不管阈值定多少，要么挡不住噪点，要么漏掉这种翻页。这个判据从根上就不对。

换成墨迹掩码的杰卡德距离：每帧自己跑一遍 Otsu 分出「有字的地方」，然后算两个掩码的异或除以并集。好处是不受页面多满、整体多亮影响——稀疏页和满页的翻页都是 0.77，整页变亮只有 0.035，因为 Otsu 跟着亮度的变化走了。阈值最后定 0.30，离两头的 0.03 和 0.77 都很远。

改完再测：同一页连发四帧全 `idle`，换成新页第一帧 `candidate`、第四帧 `confirm`、之后进 `cooldown`。对了。

手遮挡那行是 0.383，会误触发。目前靠「画面必须稳定三帧」和「确认后静默四秒」挡，手一直按着还是会中。我在 README 的已知问题里写清楚了，没有假装解决了。

## 摆正：一个低级 bug

`rectify` 第一版是「取面积最大的四边形」。在深色桌面的测试图上完全不生效。原因很蠢：深色桌面上，OTSU 二值化出来的掩码是「背景算前景、书页是个洞」，最大四边形就是整幅画面，然后被「已经贴满画面，跳过」那条判断吃掉了。

改成把两种极性各找一遍，候选先按面积比例（0.25~0.92）、是否贴边、长宽比筛掉不合格的，再从合格的里挑最大的。测下来 1500×1800 的斜拍图能正确校成 1151×1161，平整贴边的图不会被乱动。

双页分割也顺带修了一次。原来拿「两侧各取一段的中位数」当基准，只要有一侧采样区没落到文字上，基准就变成 0，直接放弃分割。改成拿「所有落过墨的列的中位数」，再顺着低谷找出缝隙实际占多宽、取中点。现在 2200×1500 的展开页能正确切成 1020 + 1180。

## 版面：把每行都拆成了独立段落

第一版的分段规则是「行间距小于 0.75 倍字高中位数就合并」。跑出来一整段正文被拆成了四五个块。

原因是 OCR 给的行框贴得很紧，而真实书的行距大概是字高的 1.3~2 倍，这个阈值定得比实际行距还小。

重写成：先算同一栏里相邻两行顶边的中位距离，当作行距；只要「行间距不超过行距的 0.7 倍」就并到同一段。另外加了风格判断——字号差太多的行（标题挨着正文）不合并。改完双页展开从 12 块降到 7 块，两段正文各自完整，标题和图注也分对了。

## 两个小毛病

`qwen3` 会把思考开关当正文吐出来，有一段译文末尾多了 `/no_think`。加了个正则把 `no_think`、`think` 和 `<|...|>` 之类的控制串清掉。

前端沉浸模式的字号自适应，第一版用二分法把文字缩到能塞进框里为止，结果长段落缩成了蚂蚁字。加了 10px 下限，塞不下就不再缩，改成让框往下长，最多长到原高度 1.5 倍。代价是会和下一块的框重叠一点，但下一块在 DOM 里靠后、盖在上面，看起来还算干净。

没有真机，所以能自动验的都验了：

- 流水线：合成一张双页展开图从 `/api/ingest` 进去，双页正确切分，12 行正文并成 7 个块，标题/图注分类正确，译文按编号对齐，总耗时约 6 秒。

- 重复页面：同一张图连传两次，第二次识别为重复，不新增页面，只把阅读位置跳回第 1 页。
- 竖版单页：不被切分。
- 摆正：斜拍 + 深色桌面能校正，平整贴边的图不动。
- 证书：`run.py` 签出的证书 SAN 里带 `DNS:localhost`、`IP:127.0.0.1` 和实际局域网 IP，有效期到 2029 年 1 月，HTTPS 能正常握手。
- 前端：三个页面的静态资源都 200，两份 JS 过 `node --check`，然后在真实浏览器里打开阅读页，逐个切了轻量、标准、沉浸三种模式，确认布局和覆盖框都正常。

## 中途卡住的一次

改完代码重启服务，测出来还是旧行为，一度以为改动没生效。查了半天发现是端口被上一次的服务占着，新进程启动时报了 `WinError 10048` 直接退了，请求其实一直打在旧进程上。

绕过的方式有点绕：我原本用 `Get-CimInstance Win32_Process` 按命令行找进程，但这台机器上 CIM 查询被拒，脚本静默返回空，等于没杀。改用 `netstat -ano` 找监听端口的 PID 再杀，才干净了。以后在这台机器上重启服务都得走 netstat。

## 没做和没验的

方案里划到范围外的都没碰：iOS 原生 App、锁屏持续采集、USB 摄像头、云端协作。

真正需要真机才能回答的问题，现在都还是问号：

1. iPhone 前置/后置在 Safari 里到底能给到多高的采集分辨率。代码里已经把它显示在取景页上（「采集分辨率」），拿到真机跑一次就有答案。
2. 手机架在支架上连续跑一两个小时会不会过热降频、Safari 会不会被系统回收。
3. 真实纸质书上，书脊弯曲和反光会把 OCR 拉到什么程度。合成图上看不出来。
4. 用真实的英文书页测翻页阈值 0.30 是不是合适。合成数据只能定个量级，真正的相机噪声、自动曝光、自动对焦还没进来。

## 关于用 Ollama 省 token

翻译走本机 Ollama 是方案本身的要求，正好也是省 token 的地方：预研阶段用来比模型的那几段翻译、以及后面所有实际翻译，都不花外部额度。文档和代码是我自己写的，没让模型代笔——这类需要贴着实现细节写的东西，转一手反而更容易写成套话。
